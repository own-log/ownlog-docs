1. 프로젝트와 제약

OwnLog(온로그)는 가입하면 /@아이디 블로그가 생기는 멀티유저 블로그다. 과제 조건만 채우면 다른 결과물과 구별되지 않아서, 기록에 시간 축(정해진 시각에 열리는 타임캡슐)과 연결 축(글끼리 [[링크]], 그 연결을 별과 선으로 보여 주는 "기록 우주")을 더했다.

2. 하네스: AI를 안전하게 일하게 만드는 장치

AI 모델이 엔진이라면 하네스는 차체·계기판·브레이크다. 엔진이 좋아도 브레이크가 없으면 맡길 수 없다. 이번 프로젝트에서는 두 종류의 하네스를 썼다.

2-1. 개발 하네스 (Claude Code)

장치무엇을효과
CLAUDE.md매 세션 자동으로 읽는 프로젝트 규칙: 기술 버전, 응답 형식, 완료 기준 7단계, Git Flow, 트러블슈팅 기록 규칙세션이 바뀌어도 같은 기준. 최신 버전에서 예전 API를 쓰는 실수 방지
권한 3단계바로 해도 됨 / 먼저 물어봄(삭제, 새 라이브러리, DB 구조, 배포 설정, main 병합) / 하지 않음(비밀값 기록, force push)길게 자율로 맡겨도 위험한 지점에서 멈춤
메모리"배포 전 배포 설명서 먼저 읽기", "큰 단위로 진행하고 스스로 검증한 뒤 짧게 보고"내 피드백이 다음 세션에도 유지

3. AI에게 맡긴 것 vs 직접 검증한 것

솔직하게 말하면 코드와 문서의 대부분은 AI가 썼다. 그래서 내 역할은 타이핑이 아니라 결정·규칙·운영 환경·검증 기준이었다.

영역AI나
방향선택지와 추천안MVP 범위, 독창 기능 방향, 디자인 방향, 출시 시점 결정
규칙CLAUDE.md 초안권한·완료 기준·Git Flow 확정
구현백엔드·프론트·마이그레이션·배포 스크립트·문서결과 확인, 방향 수정
운영 환경명령어·절차 안내서버 Nginx 설정 정리, GitHub Secrets 등록, SSH 키 등록과 작업 후 삭제
학습실습 설계와 질문리버스 프록시·헤더·포트·헬스 체크를 직접 명령으로 확인

AI를 그대로 믿지 않은 이유는 실제로 AI의 수정이 틀린 적이 있기 때문이다.

AI가 한 일잡아낸 장치
"두 번 클릭 방지"를 React state로 넣고 고쳤다고 보고화면 점검이 여전히 두 번 등록되는 것을 잡음
버그를 고치면서 새 버그(음수 진행률)를 만듦화면 점검을 반복 실행하자 3번 중 1번 실패
서버가 아예 뜨지 않는 코드(빈 순환 참조)통합 테스트 14개 전부 실패 → 운영에 가지 않음
로컬 테스트를 통과한 기능을 배포내가 운영에서 써 보다 동작 이상을 발견
문서에 과장된 수치("쿼리 0개 수정")내가 재확인 요청 → 실제로 세어 정정

4. 의도 → 구현 → 측정: 대표 사례 4가지

4-1. 타임랩스: 측정이 틀린 의도를 드러냄

문제 ▶를 누르면 별이 하나씩 태어나야 하는데, 운영에서 0.2초 만에 별 27개 중 24개가 나타나고 이후 변화가 없었다.
원인 첫 글 시각부터 지금까지 시간 비례로 재생했다. 운영 데이터는 글이 몇 분 안에 몰려 있었고, 테스트 데이터는 날짜가 고르게 퍼져 있었다.
해결 시간 대신 쓴 순서로 재생. 운영에서 0.2초 0개 → 1초 2개 → 2초 5개 → 4초 10개 → 6초 16개로 늘어나는 것을 확인했다.
함정 고친 직후 가끔 오류 화면이 떴다. requestAnimationFrame이 넘기는 시각은 그 프레임의 시작 시각이라, 버튼을 누른 순간보다 이를 수 있다.

const startedAt = performance.now()
const step = (now) => {
  // now가 startedAt보다 이를 수 있어서 0~1로 묶는다
  const progress = Math.min(1, Math.max(0, (now - startedAt) / duration))
  setCount(Math.floor(progress * total))
}

4-2. 비공개 글이 새는 경로를 구조로 막기

문제 목록·검색·태그·링크·그래프마다 "비공개·봉인 캡슐은 빼라"를 다시 쓰면 한 곳만 빠뜨려도 유출이다.
해결 공개 판단을 JPQL 상수 하나와 엔티티 메서드 하나에만 두고 재사용한다.

// 단순화 예시
public static final String PUBLIC_CONDITION = """
    p.status = PostStatus.PUBLISHED and p.visibility = Visibility.PUBLIC
    and c.visibility = Visibility.PUBLIC
    and p.publishedAt <= current_timestamp   -- 봉인된 타임캡슐은 열릴 때까지 제외
    """;

결과 타임캡슐을 추가할 때 JPQL 6개는 수정 없이 따라왔고, 네이티브 SQL 1곳만 따로 고쳤다. 조회 경로마다 누수 테스트를 남겼다.

4-3. 무중단 배포: 공용 Nginx를 건드리지 않고

문제 배포할 때마다 컨테이너를 내렸다 올려서 수십 초 동안 접속이 실패했다. 앞단 Nginx는 내가 바꿀 수 없었다.
해결 공용 Nginx 뒤에 우리 Nginx 컨테이너를 한 단 더 두고 블루-그린으로 전환한다.

# 단순화 예시
docker run -d --name ownlog-green -e SERVER_PORT=8362 ownlog:new
until curl -fs localhost:8362/api/topics; do sleep 2; done   # -f: 400 이상이면 실패
sed -i 's/8361/8362/' proxy/ownlog.conf && docker exec ownlog-proxy nginx -s reload
sleep 10 && docker stop -t 30 ownlog-blue   # Spring graceful shutdown(20초)보다 길게
상황 (로컬, 같은 스크립트)요청실패
블루-그린 배포 2회13,3080
새 버전이 못 뜨는 배포 (DB 비밀번호를 일부러 틀림)10,3950 (전환하지 않음)
예전 방식 (끄고 켜기)3,966308

함정 curl은 401·500도 "응답이 왔으니 성공(종료 코드 0)"으로 본다. -f 한 글자가 빠지면 고장 난 새 버전으로 전환된다. 그리고 이 측정은 로컬 값이다. 운영 반영은 아직 확인하지 못했다.

4-4. 관련 글 선: "많다"와 "의미 있다"는 다르다

문제 태그를 하나라도 같이 쓰면 선을 이었더니, "여행" 같은 흔한 태그 하나로 우주가 거미줄(선 36개)이 됐다.
해결 제목·요약·태그의 TF-IDF 유사도 0.3 이상, 별마다 상위 3개만.
결과 같은 데이터에서 관련 선 36 → 2개, 글 500개 합성 데이터에서 44~103ms. 기준값별 결과(0.25 → 5개, 0.15 → 19개)를 기록해 두고 근거를 갖고 조정할 수 있게 했다.

5. 백엔드에서 꼭 짚은 것: 롤백·동시성·인덱스·병목

5-1. 트랜잭션 롤백

회원가입은 회원 → 블로그 → 기본 카테고리를, 탈퇴는 글·좋아요·북마크 삭제와 개인정보 익명화를 한 트랜잭션으로 묶었다. 중간 단계를 일부러 실패시키는 테스트로 앞 단계까지 모두 되돌아가는 것을 확인했다.

5-2. 동시성 (Lost Update)

좋아요를 "읽고 → 1 더해 → 저장"하면 동시 요청이 서로 덮어쓴다. 애플리케이션이 계산하지 않고 DB가 직접 더하게 했다.

// 단순화 예시
// INSERT INTO post_likes ... ON CONFLICT DO NOTHING  → 새로 넣었으면 1, 이미 있으면 0
if (postLikeRepository.insertIfAbsent(userId, postId) == 1) {   // 실제로 새로 눌렀을 때만
    postRepository.increaseLikeCount(postId);  // UPDATE posts SET like_count = like_count + 1
}

테스트: 서로 다른 회원 100명 동시 좋아요 → 정확히 100, 한 회원이 동시에 10번 → 정확히 1, 50명 동시 조회 → 조회수 정확히 50.

5-3. 인덱스와 N+1

목록은 DTO 프로젝션으로 가져와서, 메인 목록은 카드 수와 상관없이 SQL 2개(목록 + 개수) 이하, 댓글 6개 조회는 5개 이하인 것을 Hibernate 통계로 테스트한다. 반대로 아직 하지 않은 것도 있다. 댓글 parent_id, 글 category_id에는 인덱스가 없어서 댓글·글 삭제와 탈퇴 때 표 전체를 훑는다. 데이터가 적은 지금은 문제가 없지만, 새 마이그레이션이 필요한 변경이라 결정을 미뤄 두었다.

5-4. 트래픽이 늘면 어디가 먼저 막힐까

  • 검색: 지금은 LIKE 검색이라 글이 많아지면 느려진다. pg_trgm 또는 전문 검색이 다음 단계다.
  • 기록 우주: 별 300/500개, 선 1,000/1,500개 상한을 둬서 응답 크기를 묶었다.
  • 서버 여러 대로 늘릴 때: 소셜 로그인의 1회용 코드와 state를 서버 메모리·세션에 둔다. 한 대일 때는 괜찮지만, 여러 대가 되면 공유 저장소(예: DB나 서명된 쿠키)로 옮겨야 한다.
  • 배포 동시 실행: 배포 스크립트에 잠금이 없어 두 배포가 겹치면 서로를 지울 수 있다. flock이나 Actions concurrency로 막는 것이 남은 일이다.

6. 하네스가 막지 못한 것

새어 나간 것왜보완
커밋하면 안 되는 파일을 AI가 스테이징 (푸시 전 발견)금지 규칙이 문서에만 있었음.gitignore로 구조화
배포 스크립트 로컬 시험 중 다른 Docker 이미지 삭제운영용 정리 단계가 로컬에서도 실행시험용 스위치 추가
운영 배포 결과 미확인AI가 비공개 저장소의 Actions 로그를 볼 수 없음사람이 확인, 릴리스 절차에 운영 버전 확인 명시
테스트 데이터 ≠ 운영 데이터시연 데이터의 날짜 분포가 운영과 달랐음운영 데이터 모양을 재현한 회귀 점검

7. 체크리스트

AI와 개발할 때 다시 쓸 체크리스트
☐ 규칙 파일에 "바로 / 먼저 물어봄 / 하지 않음"을 나눠 적었나
☐ 완료 기준이 "구현"이 아니라 "테스트·측정"인가
☐ 테스트 DB가 운영 DB와 같은 종류인가
☐ 테스트 데이터가 운영 데이터의 모양(분포)을 닮았나
☐ 금지 사항을 문서가 아니라 구조(.gitignore, 권한)로 막았나
☐ 헬스 체크가 상태 코드까지 보는가 (curl -f)
☐ "푸시했다"와 "운영에 반영됐다"를 따로 확인했나
☐ AI가 쓴 핵심 코드를 내가 설명할 수 있나

8. 마치며

AI에게 많이 맡길수록 내가 해야 할 일은 줄어드는 게 아니라 바뀌었다. 무엇을 만들지 정하고, 어디서 멈추게 할지 규칙으로 적고, 결과를 무엇으로 믿을지 기준을 세우는 일이었다. 가장 크게 배운 건 "됐다"는 말보다 측정값을 믿는 습관이다. 다만 코드의 대부분을 AI가 쓴 만큼, 내가 모든 코드를 설명할 수 있는 수준은 아직 아니다. 그래서 리버스 프록시, 헤더, 포트, 헬스 체크를 직접 명령으로 따라가는 실습을 시작했다.

다음 글에서는 그 실습 내용, Nginx 리버스 프록시와 X-Forwarded-Proto를 curl로 직접 확인해 본 과정을 정리할 예정이다.
