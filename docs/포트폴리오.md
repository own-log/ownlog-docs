## 2. 이력서용 문장

### 짧은 버전 (이력서 프로젝트 칸, 3~5줄)
- **OwnLog**: 멀티유저 블로그 플랫폼 1인 개발 및 운영 배포 (Spring Boot 4 · React 19 · PostgreSQL, 2주)
- 공용 Nginx 뒤에 자체 프록시를 두고 **블루-그린 무중단 배포** 구축(헬스 체크 통과 후에만 전환, 배포 중 요청 13,308건 실패 0), 서버 메모리의 OAuth 상태를 공유 DB로 옮겨 전환 중 로그인도 유지
- 전체 코드 보안 점검으로 **운영 서버의 인증 우회(URL 인코딩)·파일 삭제 IDOR·오픈 리다이렉트**를 재현하고 수정, 회귀 테스트 추가
- 좋아요·조회수 Lost Update를 **원자적 UPDATE + DB 제약**으로 차단(동시 100명 정확도 100%), 롤백되지 않는 이미지 파일은 **커밋 후 삭제(`AFTER_COMMIT`) + 유예 정리 배치**로 DB와 정합성 유지
- Testcontainers 통합 테스트 213개 + 헤드리스 Chrome 화면 점검 125개, GitHub Actions 자동 배포(동시 실행 잠금·다시 빌드 없는 롤백), Git Flow·SemVer 도입

### 긴 버전 (포트폴리오·자기소개서용 bullet)
- **설계**: 요구사항 104개를 ID로 명세하고 API 47개를 먼저 확정(API First, 이후 소셜 로그인 등을 더해 51개). 회원:블로그를 1:N으로 설계해 다중 블로그 확장 시 테이블 변경이 필요 없게 했어요.
- **정합성**: "누가 이 글을 볼 수 있는가"를 쿼리 상수 하나와 엔티티 메서드 하나로 모아, 타임캡슐·받는 사람 캡슐 같은 새 규칙을 **한 곳 수정으로** 모든 기능(목록·검색·댓글·좋아요·링크·그래프)에 적용했어요.
- **보안**: 출시 전 전체 점검에서 운영 환경 취약점 3건(인증 우회, IDOR, 오픈 리다이렉트)과 정합성·화면 버그 15건 이상을 찾아 수정하고, 고치지 않은 항목은 근거와 함께 문서화했어요.
- **배포**: 화면과 API를 Docker 이미지 하나로 묶고 GitHub Actions로 자동 배포했어요. 컨테이너가 내부망 DB에 닿지 않던 문제를 **자가 진단 배포 스크립트**로 원인(Docker 네트워크)까지 찾아 해결했어요. 이후 **블루-그린 무중단 배포**로 바꿔 배포 중 요청 실패를 0으로 만들었어요.
- **품질**: 기능마다 권한 케이스(남의 것·비공개·비로그인) 테스트를 완료 기준으로 두고, 화면 점검이 **제 수정의 오류**까지 잡아내는 회귀 체계를 만들었어요.

## 3. 문제 해결 사례 (STAR)

> 면접에서 가장 많이 묻는 "어려웠던 문제" 답변용이에요. 각 사례는 30초(요약) / 2분(전체) 두 버전으로 말할 수 있게 준비하세요.
> [트러블슈팅 기록의 대표 사례](트러블슈팅.md#대표-사례)와 같은 5건이에요. **동시성 → 트랜잭션 → 무중단 배포 → 그 후속(상태 공유·보안) → 보안** 순서라, 백엔드 핵심 주제를 하나씩 대표해요.

### 사례 1. 동시 요청에서도 정확한 좋아요·조회수
| | |
|---|---|
| **Situation** | 인기 글에 동시 요청이 몰리면 엔티티를 "읽고 +1 해서 저장"하는 방식은 값이 사라져요(Lost Update). 설계 단계에서 이 위험을 확인했어요 |
| **Task** | 락 없이 가볍게, 그러면서도 정확하게 세야 했어요 |
| **Action** | 카운터를 **DB가 직접 더하게**(`SET like_count = like_count + 1`) 하고, 엔티티 필드를 `insertable/updatable=false`로 막아 다른 수정이 예전 값으로 덮어쓰지 않게 했어요. 중복 좋아요는 복합 PK + `ON CONFLICT DO NOTHING`, 실제로 저장된 행이 있을 때만 수를 올려요 |
| **Result** | `ExecutorService`·`CountDownLatch` 동시성 테스트: 회원 100명 동시 좋아요 → **100**, 한 회원 10번 연타 → **1**, 50명 동시 조회 → **50** |
| **배운 점** | 단순 증감은 비관적·낙관적 락보다 **원자적 UPDATE + DB 제약**이 가장 싸고 확실해요 |
| **근거** | [트러블슈팅 6번](트러블슈팅.md#6-조회수좋아요가-동시-요청에서-틀어질-위험-lost-update) |

### 사례 2. 롤백되지 않는 파일을 DB 트랜잭션에 맞춰 정리했어요
| | |
|---|---|
| **Situation** | 이미지는 고르는 즉시 업로드(`POST /api/images`)되고, 글 저장은 **다른 요청**이에요. 이미지만 올리고 글을 저장하지 않으면 업로드 폴더가 43 → 44개로 늘어 그대로 남았고, 글 삭제·수정·탈퇴에도 파일을 지우는 흐름이 없었어요 |
| **Task** | 트랜잭션으로 묶을 수 없는 디스크 파일을, **DB가 롤백돼도 깨지지 않게** 정리해야 했어요 |
| **Action** | 글 삭제·수정·임시저장·탈퇴를 "주소 수집 → DB 변경 → **flush** → 아무 데서도 안 쓰면 → **커밋 뒤에**(`@TransactionalEventListener(AFTER_COMMIT)`) 파일 삭제"로 통일했어요(수정은 뺀 이미지만). 참조 확인은 JdbcTemplate으로 DB를 직접 봐서, 그 전에 JPA 변경을 명시적으로 flush해요. 기존 확인 메서드는 내 프로필을 빼고 봐서 프로필 사진까지 지울 수 있어, "어디서든 쓰나"(`isUsedAnywhere`)를 따로 만들었어요. 업로드만 하고 버려진 파일은 매일 04:00 배치가 **24시간 지난 것만** 지우고, 블루-그린 중 두 앱이 동시에 돌지 않게 `pg_try_advisory_xact_lock`을 걸었어요 |
| **Result** | 테스트 10개 추가(롤백 시 파일 유지, 프로필 함정, 유예 시간, 동시 실행 잠금), 전체 205개 통과. **일부러 깨 보기**로 각 장치가 실제로 필요한지 확인했어요: flush를 빼면 삭제 테스트가 "파일이 아직 있다", `AFTER_COMMIT`을 빼면 롤백 테스트가 "파일이 없다"로 실패해요 |
| **배운 점** | 파일처럼 **되돌릴 수 없는 부수 효과는 DB가 확정된 뒤에만** 실행해요. JPA 변경은 flush 전까지 DB에 없어서, DB를 직접 보는 확인 앞에는 flush가 필요해요 |
| **근거** | [트러블슈팅 23번](트러블슈팅.md#23-글을-지우거나-고쳐도-이미지-파일이-계속-쌓임) |

### 사례 3. 배포할 때마다 죽던 사이트를 블루-그린으로 무중단 배포했어요
| | |
|---|---|
| **Situation** | 베타 테스터가 쓰는 중에도 하루 여러 번 배포했는데, 스크립트가 서비스 중인 앱을 **먼저 끄고**(`docker rm -f`) 새 앱을 띄웠어요. Spring이 뜨는 20~40초 동안 모든 요청이 502였고, 새 버전이 못 뜨면 고칠 때까지 사이트가 죽어 있었어요 |
| **Task** | 앞단의 공용 Nginx는 포트 8360 하나만 알고 설정은 강사님만 바꿀 수 있었어요. 이걸 건드리지 않고 무중단으로 바꿔야 했어요 |
| **Action** | 공용 Nginx 뒤에 **우리 Nginx 컨테이너를 한 단계 더** 두고 blue(8361)/green(8362)을 번갈아 써요. ① 쉬는 색에 새 버전을 띄우고 그 포트로 직접 헬스 체크, **실패하면 여기서 멈춰** 예전 버전이 계속 응답해요 ② 통과하면 프록시 포트만 바꾸고 `nginx -s reload` ③ 10초 뒤 예전 버전을 `docker stop -t 30`으로 끄고, Spring은 `server.shutdown: graceful`로 처리 중인 요청을 마쳐요. 두 버전이 잠깐 같은 DB를 쓰므로 마이그레이션은 **추가만 하는 방식(expand)** 으로 정했어요 |
| **Result** | 같은 스크립트를 로컬에서 돌리며 요청을 쉬지 않고 보냈어요. 블루-그린 2회 **13,308건 중 실패 0**, 새 버전이 못 뜨는 배포(DB 비밀번호를 일부러 틀림)도 **10,395건 중 실패 0**(전환하지 않고 멈춤). 예전 방식은 3,966건 중 308건 실패(약 6초 502)였어요. 이후 배포 동시 실행 잠금(Actions `concurrency` + 서버 `flock`)과 다시 빌드하지 않는 롤백 워크플로까지 붙였어요 |
| **배운 점** | 무중단은 "빨리 바꾸기"가 아니라 **"준비가 확인된 다음에만 바꾸기"** 예요. 바꿀 수 없는 인프라가 있으면 그 앞에 **내가 통제하는 계층을 하나 더** 두면 돼요 |
| **근거** | [트러블슈팅 16번](트러블슈팅.md#16-배포할-때마다-사이트가-수십-초-동안-죽음), [22번](트러블슈팅.md#22-배포가-겹칠-수-있고-롤백하려면-다시-빌드해야-했음) |

### 사례 4. 무중단 배포가 만든 새 문제: 전환 순간의 소셜 로그인 실패
| | |
|---|---|
| **Situation** | 소셜 로그인 점검에서 "세션 없이 콜백이 오면?"을 실제로 보내 보니 `authorization_request_not_found`로 실패했어요. 블루-그린 배포 중 **blue에서 동의 화면으로 갔다가 green으로 돌아오는** 사람이 정확히 이 상태가 돼요 |
| **Task** | 두 서버가 잠깐 함께 떠 있는 구조에서 로그인 중간 상태를 공유하되, 그 상태가 원래 막던 **로그인 CSRF는 다시 열지 않아야** 했어요 |
| **Action** | 원인은 Spring Security가 인가 요청(state 포함)을 기본으로 **서버 메모리 세션**에, 로그인 후 1회용 코드를 `ConcurrentHashMap`에 둔 것이었어요. Flyway V7로 두 서버가 함께 쓰는 DB 테이블(인가 요청 5분, 코드는 SHA-256 해시만 60초)을 만들었어요. 저장소(`JdbcOAuth2AuthorizationRequestRepository`)는 같은 state를 쿠키로도 주고, 돌아왔을 때 **주소의 state = 쿠키의 state**일 때만 `DELETE … RETURNING`으로 꺼내요. DB만 보면 남이 만든 state도 통과하기 때문이에요. 1회용 코드도 `DELETE … RETURNING` 한 문장으로 꺼내 동시에 두 번 와도 한 번만 성공해요 |
| **Result** | 실제 서버 2대(8081=blue, 8082=green, 같은 DB)로 8081에서 시작 → 8082로 돌아와도 state 확인을 통과했어요(수정 전엔 실패). 쿠키 없이 보내면 여전히 거부되고, 세션 쿠키는 아예 생기지 않아요. 테스트 6개 추가(다른 서버 이어짐·한 번만, 다른 브라우저 거부, 만료, 동시 교환 1회만) |
| **배운 점** | 무중단 배포를 하면 **"서버 메모리에 무엇을 두고 있나"** 를 다시 봐야 해요. 상태를 공유 저장소로 옮길 때는 **원래 그 상태가 막던 공격**이 다시 열리지 않는지 함께 봐야 해요 |
| **근거** | [트러블슈팅 24번](트러블슈팅.md#24-블루-그린-전환-순간에-소셜-로그인이-실패함) |

### 사례 5. 운영 서버의 인증 우회 취약점을 재현하고 막았어요
| | |
|---|---|
| **Situation** | 출시 전, 백엔드·프론트엔드 전체를 보안·성능·정합성으로 나눠 점검했어요 |
| **Task** | 실제로 악용 가능한 문제를 찾아 **운영에 영향 없이** 확인하고 고쳐야 했어요 |
| **Action** | `/api/users/me`는 401인데 `/%61pi/users/me`(`%61`=a)는 500이 나는 걸 발견했어요. 상태를 바꾸지 않는 GET으로 **운영 서버에서도 재현**했어요. 원인은 인가 규칙이 **디코딩 전 주소**(`getRequestURI`)로 "API가 아니다"라고 판단하고, MVC는 **디코딩 후 주소**로 API를 실행하는 해석 차이였어요. 같은 방식으로 로그인 없이 이미지 업로드도 가능했어요. MVC와 같은 기준으로 비교하는 경로 패턴 매처(`/api/**`)로 바꾸고, MockMvc가 주소를 재인코딩하지 않게 `URI.create`로 보내는 회귀 테스트를 만들었어요 |
| **Result** | 운영에서 같은 요청이 **401**로 막히는 것을 배포 후 확인했어요. 같은 점검에서 IDOR(남의 파일 삭제), 오픈 리다이렉트까지 **보안 8건**을 수정하고 백엔드 테스트를 159 → 169개로 늘렸어요 |
| **배운 점** | 보안 규칙은 실제로 요청을 처리하는 계층과 **같은 해석 기준**을 써야 해요 |
| **근거** | [트러블슈팅 2번](트러블슈팅.md#2-인코딩한-주소로-로그인-검사를-건너뜀-인증-우회) |

> 추가 사례(필요한 회사에 맞춰 교체): 자가 진단 배포 스크립트(1), 공개 조건 일원화와 타임캡슐(7), 회귀 점검이 잡은 내 수정 오류(10), 오픈 리다이렉트(4), BCrypt 72바이트 한글 비밀번호 500(5), 저장된 요약 데이터 마이그레이션(8), 401 인터셉터 설계(9), 타임랩스 렌더링 최적화(11) → [트러블슈팅 기록](트러블슈팅.md)의 괄호 속 번호

## 4. 기술적 의사결정

| 결정 | 고른 것 | 버린 대안과 이유 |
|---|---|---|
| 타임캡슐 구현 | `published_at` = 개봉 시각 + `sealed_at` | 별도 테이블·스케줄러: 모든 목록 쿼리 수정과 배치 실패 지점이 생겨요 |
| 카운터 동시성 | 원자적 UPDATE + DB 제약 | 비관적 락(대기), 낙관적 락(재시도 처리) |
| 목록 조회 | `select new` DTO 프로젝션 | 엔티티 + fetch join 페이징: 메모리 페이징·본문까지 읽음 |
| 스키마 관리 | Flyway + `ddl-auto: validate` | `ddl-auto: update`: 부분 인덱스·CHECK 불가, 운영 변경 추적 불가 |
| 토큰 저장 | localStorage + sanitize 전제 | HttpOnly 쿠키: CSRF 대응·서버 설정 추가 (2차에 Refresh Token과 재검토) |
| 파일 삭제 권한 (점검 후) | 지우기 전 참조 확인 | 소유자 테이블: 정확하지만 마이그레이션·이관 필요 → 2차 |
| 그래프 렌더링 | d3-force(배치) + Canvas | SVG: 노드 수백 개에서 DOM 비용, 차트 라이브러리: 번들 증가 |
| 배포 단위 | 화면+API 단일 이미지 | 분리 배포: CORS·이중 파이프라인 (수업 서버 포트 1개 제약) |
| 브랜치 전략 | Git Flow + SemVer | GitHub Flow: 더 가볍지만 main 푸시 = 배포라 운영 버전 분리가 필요했어요 |

## 6. 일하는 방식 (AI 협업 포함)

- **API First와 요구사항 ID**: 기획 단계에서 요구사항 104개를 ID로 쪼개고, 코드·테스트·문서가 같은 ID를 가리키게 했어요(예: `(TC-03)`).
- **AI 페어 프로그래밍**: Claude Code에 구현을 맡기되, 정책 결정·설계 승인·검증 기준은 제가 정했어요. `CLAUDE.md`에 작업 권한(삭제·DB 구조·배포 설정은 사전 확인), 코드 규칙, **완료 기준**(권한 테스트, 문서 동기화, CHANGELOG)을 명시해 일관성을 유지했어요.
- **검증 우선**: AI가 만든 코드든 제가 결정한 설계든, 백엔드 통합 테스트와 화면 점검을 통과해야 병합해요.
- **기록**: 트러블슈팅 26건([대표 사례 5건](트러블슈팅.md#대표-사례)), 점검 보고서, 변경 기록(CHANGELOG), 버전 태그(v0.1.0 ~ v1.3.0)로 의사결정 과정을 남겼어요.

## 7. 회고와 다음 단계

**잘한 점**
- 기능보다 **구조**(공개 조건 일원화, DB 제약)에 먼저 투자해서, 막바지에 기능을 빠르게 늘려도 사고가 나지 않았어요.
- 출시 전에 스스로 **전체 점검**을 해서, 사용자가 겪기 전에 운영 취약점을 찾았어요.

**아쉬운 점과 개선 계획** (README "앞으로의 계획")
| 우선순위 | 항목 | 이유 |
|---|---|---|
| 1 | 업로드 소유자 기록, 이미지 리사이즈·EXIF 제거 | 사례 1의 IDOR를 근본적으로 해결, 성능·개인정보 |
| 2 | Refresh Token(HttpOnly), 요청 횟수 제한 | 인증 강화, 무차별 대입 방지 |
| 3 | 댓글 `parent_id` 인덱스, 검색 `pg_trgm` | 점검에서 찾은 확장성 병목 |
| 4 | 알림(캡슐 개봉, 글 연결) | 기록 유니버스와 가장 잘 어울리는 다음 기능 |
