## 0. 요약

**의도:** 과제 조건(멀티유저 블로그)만 채운 결과물과 구별되도록, 기록에 **시간 축과 연결 축**을 더한 "기록 유니버스"를 만들고, 그 기능이 **보안·데이터 무결성·배포 안정성을 해치지 않게** 한다.

**방법:** AI(Claude Code)가 코드와 문서의 대부분을 작성하고, 사람은 **방향·결정·운영 환경**을 맡았어요. 완료 여부는 AI의 "됐어요"가 아니라 **테스트·화면 점검·측정 결과**로만 판단했어요.

| 지표 | 값 | 비고 |
|---|---|---|
| 기간 / 인원 | 14일 / 1명 + AI | 실제 커밋이 있는 날은 7일 |
| 커밋 / 병합 | 97 / 18 (`--no-ff`) | 97개 중 79개에 AI 공동 작성 표기 |
| 버전 | v0.1.0 ~ v1.2.1 (태그 11개) | SemVer, CHANGELOG |
| 코드 (줄) | 백엔드 7,117 · 프론트 4,137 | `java·jsx·js·sql` 기준 |
| 테스트 코드 (줄) | 백엔드 테스트 4,669 · 화면 점검 1,726 | 테스트 줄 수가 백엔드 코드의 약 66% |
| API | 매핑 51개 | 컨트롤러 `@*Mapping` 기준 |
| 백엔드 통합 테스트 | **193개 통과** | 실제 PostgreSQL(Testcontainers) |
| 화면 점검(e2e) | **125개 통과** (점검 14종) | 헤드리스 Chrome, 별도 DB 스키마 |
| 트러블슈팅 기록 | 20건 | 상황 → 원인 → 해결 → 결과 → 배운 점 |

## 2. 의도 → 구현 → 측정

각 항목은 **의도(왜) → 구현(어떻게) → 측정(정말 됐나)** 순서예요. 측정이 의도를 증명하지 못한 경우도 그대로 적었어요.

### 2-1. 차별화: 기록 유니버스

| 의도 | 구현 | 측정 결과 |
|---|---|---|
| 글이 목록에 쌓이기만 하지 않고 **시간으로** 이어지게 | 타임캡슐(1분~10년 뒤 열림), 받는 사람 캡슐, 1년 잔디 | 봉인 중 제목·태그가 목록·검색·링크·그래프로 새지 않는지 **경로별 누수 테스트** 통과 |
| 글끼리 **연결로** 이어지게 | `[[글]]` 링크·백링크·미리보기, 기록 우주(d3-force + Canvas), 타임랩스 | 아래 2건은 측정이 **문제를 드러낸** 사례예요 |

**측정이 문제를 드러낸 사례 ① 타임랩스 (v1.0.1)**
- 의도: ▶를 누르면 별이 하나씩 태어나며 우주가 자란다.
- 처음 구현: 첫 글 시각 → 지금까지 **시간 비례**로 재생. 로컬 테스트는 통과했어요(테스트 데이터는 날짜가 고르게 퍼져 있었어요).
- 운영 측정: 재생 0.2초 만에 **별 27개 중 24개**가 나타나고 이후 변화가 없었어요. 운영 데이터는 글이 몇 분 안에 몰려 있었어요.
- 수정 후 측정: **쓴 순서** 기준 재생 → 운영에서 0.2초 0개 → 1초 2개 → 2초 5개 → 4초 10개 → 6초 16개로 점점 늘어나는 것 확인.

**측정이 문제를 드러낸 사례 ② 관련 글 선 (v1.2.0)**
- 의도: 관련 있는 글끼리 선으로 잇는다.
- 처음 구현: 태그를 하나라도 같이 쓰면 연결 → 전체 우주에 태그 선 **36개**, 흔한 태그 하나로 거미줄이 됐어요.
- 수정: 제목·요약·태그의 **TF-IDF 유사도** 0.3 이상 + 별마다 상위 3개.
- 측정: 같은 시연 데이터에서 관련 선 **36 → 2** (직접 건 링크 20개는 그대로). 글 500개 합성 데이터에서 계산 **44~103ms**.
- 남은 판단: 선이 적어진 만큼 덜 화려해요. 기준값별 결과(0.25 → 5개, 0.15 → 19개)를 남겨 근거를 갖고 조정할 수 있게 했어요.

### 2-2. 데이터 무결성: 비공개 글이 새지 않게

| 의도 | 구현 | 측정 결과 |
|---|---|---|
| 기능이 늘어도 비공개·봉인·받는 사람 캡슐이 새지 않게 | 공개 판단을 **두 곳**에만: `PostCardQueries.PUBLIC_CONDITION`(JPQL), `Post.isViewableBy()`(엔티티) | 타임캡슐 추가 시 JPQL 6개는 **수정 없이** 반영, 네이티브 SQL 1곳만 수정 |
| 존재 여부도 숨기기 | 볼 수 없는 대상은 404, 볼 수는 있지만 권한이 없으면 403 | 권한(남의 것·비공개·비로그인) 테스트가 기능마다 포함 |
| 관련 글 계산이 내용을 흘리지 않게 | 볼 수 없는 글은 단어 통계에도 넣지 않음 | 비공개·봉인 캡슐 연결 여부 테스트 통과 |

### 2-3. 동시성: 숫자가 틀어지지 않게

| 의도 | 구현 | 측정 결과 (테스트) |
|---|---|---|
| 좋아요·조회수가 동시 요청에서 정확하게 | 애플리케이션이 읽고 더하지 않고 **DB가 직접** `x = x + 1`. 엔티티 필드는 쓰기 금지 | 서로 다른 회원 **100명 동시 좋아요 → 정확히 100** |
| 연타해도 한 번만 | `UNIQUE` + `ON CONFLICT DO NOTHING` | 한 회원이 **동시에 10번 → 정확히 1** |
| 조회수 | 같은 방식 | 방문자 **50명 동시 조회 → 정확히 50** |
| 중간 실패 시 일부만 저장되지 않게 | 회원가입(회원·블로그·카테고리), 탈퇴(글·좋아요·북마크·개인정보)를 한 트랜잭션으로 | 중간에 일부러 실패시키는 **롤백 테스트** 통과 |

### 2-4. 보안: 점검으로 찾은 것

v0.6.0에서 전체 코드를 점검해 **실제로 재현된** 문제를 고쳤어요. 주요 3건은 심각도 "높음"이었어요.

| 문제 | 어떻게 확인 | 수정 후 |
|---|---|---|
| `/%61pi/…`로 로그인 검사 우회 | **운영 서버에서도 재현** (상태를 바꾸지 않는 요청으로) | 401, 회귀 테스트 + 화면 점검 |
| 프로필 사진 주소로 남의 업로드 파일 삭제 | 테스트로 재현 | 다른 곳에서 쓰면 지우지 않음 |
| 로그인 후 외부 사이트로 이동(오픈 리다이렉트) | 공격 주소 3종으로 재현 | 화면 점검 통과 |
| 한글 긴 비밀번호 가입이 500 (BCrypt 72바이트) | 테스트로 재현 | 400 + 입력 칸 안내 |

v1.2.0 소셜 로그인은 **편의보다 계정 안전**을 골랐어요. 같은 이메일 기존 계정에 자동 연결하지 않고, JWT 대신 60초짜리 1회용 코드를 넘겨요. 위조된 state와 재사용된 코드는 테스트로 거부되는 것을 확인했어요.

### 2-5. 성능

| 의도 | 구현 | 측정 결과 |
|---|---|---|
| 타임랩스 중 화면이 버벅이지 않게 | 애니메이션 값을 React state 대신 **캔버스에 직접** 전달 | 재생 중 페이지 전체 재렌더링 초당 약 60회 → 0회 |
| 첫 화면을 가볍게 | 무거운 화면(글쓰기·상세·우주)은 지연 로딩 | 메인 번들 **374.8KB**(gzip 119.7KB), 기준 500KB 이하. 글쓰기 화면은 별도 324KB |
| 목록 N+1 방지 | 목록은 `select new` DTO, 상세는 `join fetch` | 테스트에서 Hibernate 통계로 SQL 수를 셈: 메인 목록 **카드 수와 상관없이 2개 이하**(목록 + 개수), 3명이 쓴 댓글 6개 조회 **5개 이하** |
| 그래프 상한 | 별 300/500개, 선 1,000/1,500개 상한 | 500개 합성 데이터 44~103ms (2-1) |

### 2-6. 배포 안정성

| 의도 | 구현 | 측정 결과 |
|---|---|---|
| 첫 배포 실패 원인을 추측하지 않고 찾기 | 배포 스크립트가 서버→DB, 컨테이너→DB 연결을 **스스로 진단** | "컨테이너에서만 DB에 닿지 않음"을 찾아 `--network host`로 해결 (트러블슈팅 #1) |
| 배포해도 끊기지 않게 | 블루-그린 + 헬스 체크(`curl -fs`) + Nginx reload + graceful shutdown | **로컬** 측정: 배포 2회 중 요청 13,308건 **실패 0** / 예전 방식 3,966건 중 **308건 실패** |
| 새 버전이 망가져도 서비스 유지 | 헬스 체크 실패 시 전환하지 않음 | **로컬** 측정: DB 비밀번호를 일부러 틀린 배포 중 10,395건 **실패 0** |
| 문서만 고쳐도 배포가 돌지 않게 | 배포 제외 규칙 + 문서 저장소 분리 | 코드 저장소 설계 문서 0개, 옮긴 링크 19개 정상 |

## 3. AI에게 맡긴 것 vs 직접 검증한 것

### 3-1. 역할 나누기

솔직하게 적으면, **코드와 문서의 대부분은 AI(Claude Code)가 작성했어요.** 커밋 97개 중 79개에 AI 공동 작성 표기가 있어요. 그래서 이 프로젝트에서 사람의 역할은 "타이핑"이 아니라 아래 세 가지였어요.

| 영역 | AI에게 맡긴 것 | 사람이 한 것 | 완료를 판단한 근거 |
|---|---|---|---|
| 방향 | 선택지와 추천안 정리 | **결정**: MVP 범위, 독창 기능 방향, 디자인 방향("밝은 본문 + 우주 포인트"), 소셜 로그인 4종, "오늘 바로 출시" 같은 일정 판단 | 요구사항 명세 |
| 규칙 | CLAUDE.md 초안 | **규칙 확정**: 작업 권한(바로 / 먼저 물어보기 / 하지 않기), 완료 기준, Git Flow | CLAUDE.md |
| 구현 | 백엔드·프론트·마이그레이션·배포 스크립트·문서 작성 | 결과 확인, 방향 수정 요청 | 테스트·화면 점검 |
| 검증 | 테스트·화면 점검 작성과 실행, 부하 측정 | 운영 화면을 직접 써 보고 이상 보고(타임랩스), 베타 테스터 모집·안내 | 측정값, 운영 확인 |
| 운영 환경 | 명령어와 절차 안내 | **서버 작업**: Nginx 설정 파일 정리, GitHub Secrets 등록, SSH 키 등록·삭제(작업 후 AI의 서버 접근 회수) | 운영 응답 확인 |
| 학습 | 실습 설계와 질문 | 리버스 프록시·헤더·포트·헬스 체크를 **직접 명령으로 확인**하고 이해를 기록 (코드 저장소 `docs/learning-log.md`, `docs/learning-log` 브랜치) | 학습 기록 리뷰 |

> ✍️ **본인 확인란:** 위 "사람이 한 것"은 작업 기록에서 확인되는 것만 적었어요. 직접 코드를 읽고 고친 부분, 발표 준비 등 빠진 것이 있으면 추가해 주세요.

### 3-2. AI가 만든 오류를 무엇이 잡았나

"AI가 됐다고 한 것"을 그대로 믿지 않은 이유는 **실제로 AI의 수정이 틀린 적이 있기 때문**이에요.

| 사례 | AI가 한 일 | 잡아낸 장치 | 교훈 |
|---|---|---|---|
| 두 번 클릭 방지 (#10) | state로 막는 코드를 넣고 "고쳤다"고 함 | **화면 점검**이 여전히 두 번 등록되는 것을 잡음 | 확신보다 재현 테스트 |
| 타임랩스 순서 재생 (#14) | 13번을 고치면서 음수 진행률 버그를 새로 만듦 | **화면 점검 반복 실행**에서 3번 중 1번 실패 → 실패 화면 확인 | 가끔 실패하는 테스트를 넘기지 않기 |
| 타임랩스 시간 비례 (#13) | 로컬 테스트 통과 상태로 배포 | **사람**이 운영에서 직접 써 보다 발견 | 테스트 데이터가 운영 데이터를 닮지 않으면 테스트가 못 잡음 |
| 소셜 로그인 순환 참조 (#17) | 서버가 뜨지 않는 코드 작성 | **통합 테스트** 14개 전부 실패 | 테스트가 먼저 돌아서 운영에 가지 않음 |
| 문서의 과장된 수치 | "쿼리 0개 수정", "20여 건" 등 | **사람의 재확인 요청** → 실제로 세어 "JPQL 6개 수정 없음, 네이티브 1곳 수정", "15건 이상"으로 정정 | 문서 숫자도 측정값이어야 함 |
| 배포 설명서 PDF 커밋 | `git add -A docs`로 금지 파일을 스테이징 | 푸시 전 **AI 스스로** 커밋 내용 확인 → 제거, `.gitignore` 추가 | 금지 규칙은 구조(.gitignore)로 |
| 로컬 이미지 삭제 (#19) | 운영용 정리 단계를 로컬에서 실행 | 시험 후 **이미지 목록 확인** | 지우는 명령은 범위부터 확인 |
| 화면 점검 주소 (`check-expired`) | 점검 대상이 아닌 개발 서버 주소를 하드코딩 | 새 기능 점검 중 **실패 원인 분석** | 검증 도구도 검증 대상 |

### 3-3. 원칙
1. **완료 = 측정.** "구현했다"가 아니라 테스트 통과 수, 화면 점검 결과, 측정값으로 보고해요. 확인하지 못한 것은 "확인하지 못했다"고 써요(0장 운영 반영 상태처럼).
2. **위험한 작업은 사람이 결정.** 삭제, 새 라이브러리, DB 구조 변경, 배포 설정, `main` 병합, 외부 공개는 AI가 먼저 물어보게 규칙으로 정했어요.
3. **비밀값은 AI에게도 주지 않음.** DB·SSH 비밀번호, OAuth 키는 GitHub Secrets와 `.env`에만 두고 코드·커밋·대화에 쓰지 않아요.

## 4. 하네스로 개발한 과정

### 4-1. 하네스란
AI 모델이 **엔진**이라면, 하네스는 그 엔진을 안전하게 일하게 만드는 **차체·계기판·브레이크**예요. 이 프로젝트에서는 두 종류의 하네스를 썼어요.

```
┌─ 개발 하네스 (Claude Code) ───────────────────────────────┐
│  규칙(CLAUDE.md) · 기억(메모리) · 권한 · 병렬 작업(서브에이전트·worktree) │
└──────────────────────────┬────────────────────────────────┘
                           │ AI가 만든 결과물
┌─ 검증 하네스 ─────────────▼────────────────────────────────┐
│  통합 테스트(Testcontainers) · 화면 점검(CDP) · CI · 배포 자가 진단 · 부하 측정 │
└───────────────────────────────────────────────────────────┘
```

### 4-2. 개발 하네스

| 장치 | 무엇을 | 효과 |
|---|---|---|
| **CLAUDE.md** (매 세션 자동으로 읽는 프로젝트 규칙) | 역할·말투, 기술 버전(Spring Boot 4.1, Jackson 3 등 "예전 방식 금지"), 코드 규칙(응답 형식, 공개 조건 두 곳), 완료 기준 7단계, Git Flow, 트러블슈팅 기록 규칙 | 세션이 바뀌어도 같은 기준으로 일함. 최신 버전에서 예전 API를 쓰는 실수 방지 |
| **권한 3단계** | 바로 해도 됨 / 먼저 물어봄 / 하지 않음 | 자율로 길게 맡겨도(예: "점심시간 동안 혼자 끝까지") 위험한 작업은 멈추고 물어봄 |
| **메모리** | "배포 전 배포 설명서 먼저 읽기", "큰 단위로 진행하고 스스로 검증한 뒤 짧게 보고" | 사용자 피드백이 다음 세션에도 이어짐 |
| **서브에이전트 + git worktree** | 서로 독립적인 일을 별도 작업 폴더·브랜치에서 동시에 | v1.2.0 하루에 문서 4종(에이전트 A), 우주 연관도(에이전트 B), 무중단 배포·소셜 로그인(본체)을 병렬로 진행 → **본체가 검토한 뒤** `--no-ff` 병합 |
| **백그라운드 작업** | 테스트·이미지 빌드·부하 측정을 돌려 두고 다른 일 | 기다리는 시간 동안 문서 작성 |

### 4-3. 검증 하네스

| 장치 | 무엇을 | 만든 이유 (실제로 겪은 일) |
|---|---|---|
| Testcontainers | 테스트마다 실제 PostgreSQL 17 | 부분 인덱스·`CHECK`·`ON CONFLICT`·네이티브 SQL은 메모리 DB로 검증할 수 없음 |
| 화면 점검 (`e2e/`, CDP) | 헤드리스 Chrome으로 실제로 눌러 보는 125개 항목 | AI의 프론트 수정이 틀린 것(#10, #14)을 잡음 |
| 점검 격리 | 실행마다 새 브라우저 프로필 + 별도 DB 스키마, 명령 30초·점검 4분 제한 | 결과가 매번 달라짐(#12), 30분 멈춤(#15) |
| CI | 작업 브랜치·`develop` 푸시마다 테스트·lint·build | 합치기 전 확인 |
| 배포 자가 진단 | DB 연결을 서버/컨테이너 각각에서 확인, 실패 시 원인 출력 | 같은 오류를 값만 바꿔 반복하던 상황(#1) |
| 부하 측정 | 배포 중 요청을 쉬지 않고 보내 실패 수 세기 | "무중단"을 말이 아니라 숫자로 (2-6) |

### 4-4. 한 사이클 예시: v1.2.0 (10/13, 하루)

```
요청: "우주 연관도·무중단 배포·소셜 로그인·문서 여러 개, 오늘 출시"
 ├─ 결정 질문 2개만: 소셜 로그인 범위(4종), 출시 시점(오늘)
 ├─ 병렬: 에이전트 A(문서 4종) · 에이전트 B(연관도) · 본체(무중단 → 소셜 로그인)
 ├─ 검증: 블루-그린 부하 측정 → 소셜 로그인 테스트 14개 → 병합 후 전체 193개
 │        → 화면 점검 125개 (여기서 점검 도구 버그 1건 발견·수정)
 ├─ 기록: 트러블슈팅 16~19, CHANGELOG, 개념 가이드
 └─ 릴리스: release/1.2.0 → main → 태그 → develop
     └─ ❗ 운영 반영은 확인하지 못함 (Actions 결과를 볼 수단이 없어 사람에게 확인 요청)
```

### 4-5. 하네스가 막지 못한 것과 보완
| 새어 나간 것 | 왜 못 막았나 | 보완 |
|---|---|---|
| 금지 파일(배포 설명서 PDF) 스테이징 | 규칙은 문서에만 있었음 | `.gitignore`에 추가 (규칙 → 구조) |
| 로컬 이미지 삭제 | 운영 스크립트를 로컬에서 "그대로" 실행 | 시험용 스위치 `KEEP_IMAGES` |
| 운영 배포 결과 미확인 | 비공개 저장소의 Actions 로그를 AI가 볼 수 없음(`gh` 없음) | 사람이 Actions 확인 → 다음에는 배포 후 운영 버전 확인을 릴리스 절차에 명시 |
| 테스트 데이터 ≠ 운영 데이터 (#13) | 시연 데이터의 날짜 분포가 운영과 달랐음 | 운영 데이터 모양을 재현한 회귀 점검 |

## 5. 회고

**잘된 점**
- 독창 기능을 늘리면서도 **공개 조건을 한 곳에 모은 구조** 덕분에 새 기능이 보안 규칙을 깨지 않았어요.
- 측정을 습관으로 둬서, 측정이 **틀린 의도**(타임랩스, 관련 글 선)를 드러냈을 때 바로 고칠 수 있었어요.
- AI에게 많이 맡긴 만큼 **검증 장치에 투자**했고, 실제로 AI의 오류를 여러 번 잡았어요.

**아쉬운 점**
- v1.2.x를 운영에서 확인하지 못했어요. "푸시했다"와 "운영에 반영됐다"는 달라요.
- 테스트 데이터가 운영 데이터를 닮지 않아 사람이 찾은 버그가 있었어요.
- 코드의 대부분을 AI가 썼기 때문에, 사람이 모든 코드를 설명할 수 있는 수준은 아직 아니에요. 그래서 핵심 영역(리버스 프록시, 헤더, 포트, 헬스 체크, 무중단 배포)을 **직접 실습**하며 따라가고 있어요.
